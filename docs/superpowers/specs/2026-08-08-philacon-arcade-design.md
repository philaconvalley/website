# PhilaCon Arcade — Design Spec

**Date:** 2026-08-08
**Branch:** `waskar/philacon-arcade`
**Status:** Approved design, not yet planned or implemented

---

## 1. What this is

A new section of the site at `/arcade` that displays playable browser games built by the
PhilaCon community, presented as a wall of arcade cabinets. Launch content is three games
built by Diego Mendoza.

The arcade is a showcase, not a platform. It has no accounts, no scores server, no play
tracking, and no submission form. Games arrive as pull requests.

### Launch content

| Game                   | Size   | Input              | Notes                                                           |
| ---------------------- | ------ | ------------------ | --------------------------------------------------------------- |
| Flappy Philacon        | 140 KB | pointer + keyboard | Works on phones. Uses `localStorage` for a high score.          |
| PhilaCon Keyboard Pong | 81 KB  | keyboard only      | **Desktop only.** Fixed 860×500 canvas, no resize handling.     |
| Pigeon Post            | 21 KB  | keyboard + touch   | Depends on three.js r128. A flight demo, not a goal-based game. |

None of the three use audio. All three call `preventDefault` on their input keys.

## 2. Decisions

| Decision               | Choice                                                       | Why                                                                                                                                                                          |
| ---------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Where games run        | Embedded in a sandboxed iframe on a PhilaCon cabinet page    | The only option that feels like an arcade rather than a link list.                                                                                                           |
| Where games are hosted | Self-hosted at `public/games/<slug>/`                        | Launch content is first-party work commissioned by PhilaCon, reviewable in a PR. The third-party threat model does not apply.                                                |
| Community submissions  | Same self-hosted path, via PR                                | The external-origin lane (CSP `frame-src` allowlisting) is **cut**. It had no contributor path, no review checklist, and no one asking for it. Add it when someone does.     |
| Wall layout            | Cabinet wall — four standing cabinets                        | Three games in a grid read as a grid missing its fourth item. Four cabinets read as a lineup.                                                                                |
| Cabinet page           | Adaptive: full cabinet on desktop, honest fallback on phones | The alternatives ship a Pong cabinet that phone visitors tap and cannot play, with no explanation.                                                                           |
| Theme                  | Matches the site — cream page, dark cabinets                 | The site has no dark mode (no `prefers-color-scheme`, no `dark:` variants, no `darkMode` config). Cabinets are dark _as objects_, the way `Header` and `Footer` already are. |
| Licensing              | MIT with the rest of the repo                                | **Conditional — see §9.**                                                                                                                                                    |
| Navigation             | Eighth top-level nav item                                    |                                                                                                                                                                              |
| Screenshots            | Generated by a Playwright capture script                     |                                                                                                                                                                              |

## 3. Aesthetic direction

**"Cabinet Room."** The arcade is a room inside the house, not another page of it. Cream
page like every other page; the cabinets are the dark, lit objects standing in it.

**DFII: 14/15** — Impact 5, Fit 4, Feasibility 4, Performance 4, minus Consistency Risk 3.
The risk score is honest: the cabinet is bespoke CSS appearing on exactly two pages,
reusing nothing.

### Typography — no new typeface

The obvious move is a pixel font. It is also the most templated arcade decision available,
it would be the site's third typeface, and it fails contrast at small sizes. Baloo 2 at
weight 800 with tight tracking on a lit marquee panel already reads as arcade, because
**the cabinet silhouette carries the signal, not the letterforms.** Nunito stays for
everything actually read.

### Color

No new tokens. `brand-dark` for cabinet bodies, existing `brand-pink` / `brand-purple` /
`brand-yellow` / `brand-coral` as marquee colors — one per cabinet, which is what makes a
lineup look like a lineup. Cream returns below the wall.

**All arcade CSS uses design tokens, never hardcoded hex.** If a real dark mode is added
later, the arcade follows it rather than needing a rewrite.

### Motion — three moments

1. Cabinets rise into place in sequence on load (~60 ms stagger).
2. Hover lifts a cabinet and warms its marquee glow.
3. Control-panel keycaps depress when that key is actually pressed during play — the one
   flourish that is functional, since it teaches controls without a tutorial.

All three collapse under `prefers-reduced-motion`, which `e2e/motion-preferences.spec.ts`
already tests for.

### The fourth cabinet

Three games plus one unlit cabinet whose marquee reads **YOUR GAME HERE** and whose screen
shows a coin slot, linking to `docs/adding-content.md`. It balances the composition, makes
the arcade legibly a thing that grows, and is the element a visitor remembers a day later.

Known consequence: it invites submissions that arrive as PRs committing game code into this
repo, which is real review burden. Shipping it is a deliberate acceptance of that.

## 4. Structure

```
src/pages/arcade/index.astro      → the cabinet wall
src/pages/arcade/[slug].astro     → the cabinet page
src/components/ArcadeCabinet.astro
src/components/CabinetFrame.astro
src/content/arcade/*.md           → one file per game
public/games/<slug>/              → self-hosted game builds
scripts/capture-arcade-shots.mjs  → Playwright thumbnail + og:image capture
```

Cabinet **pages** live at `/arcade/<slug>`; raw game **files** at `/games/<slug>/`.
Separate trees on purpose: it confines the header carve-out to one path and removes any
chance of a static file shadowing the `[slug]` route.

### Collection schema (`arcade`)

| Field             | Type              | Notes                                                                                                                                |
| ----------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `title`           | string            |                                                                                                                                      |
| `contributors`    | string[]          | Array, matching `projects` and `resources`.                                                                                          |
| `description`     | string            |                                                                                                                                      |
| `longDescription` | string            | Real prose describing what the game is and how it plays — see §7.                                                                    |
| `thumbnail`       | string            | Generated.                                                                                                                           |
| `thumbnailAlt`    | string            | **Authored, required.** Playwright can make the image; it cannot describe it. `gallery` sets this precedent with its required `alt`. |
| `ogImage`         | string            | Generated, 1200×630 — a different crop from `thumbnail`.                                                                             |
| `marqueeColor`    | enum              | `pink` \| `purple` \| `yellow` \| `coral`                                                                                            |
| `kind`            | enum              | `game` \| `demo` — Pigeon Post is a demo and the cabinet says so.                                                                    |
| `input`           | enum[]            | `keyboard` \| `pointer` \| `touch`. Drives the phone fallback.                                                                       |
| `fixedSize`       | `{w, h}` optional | Present for Pong; drives the scale wrapper.                                                                                          |
| `controls`        | `{keys, label}[]` | Renders the control-panel legend as real markup.                                                                                     |
| `date`            | date              |                                                                                                                                      |

## 5. Security and headers

### The blocker

`vercel.json` currently makes this feature impossible, three ways over:

| Header                | Current                           | Effect                                                                            |
| --------------------- | --------------------------------- | --------------------------------------------------------------------------------- |
| `X-Frame-Options`     | `DENY`                            | Site pages cannot be framed at all, even by themselves.                           |
| CSP `frame-ancestors` | `'none'`                          | Same, via CSP.                                                                    |
| CSP `script-src`      | `'self' 'unsafe-eval' 'sha256-…'` | All three games are inline `<script>` with no matching hash. They do not execute. |

A self-hosted game under today's headers is a blank rectangle.

### The carve-out

Two **mutually exclusive** header rules, not one overriding the other:

- Global rule source narrowed to `/((?!games/).*)` — every real page keeps today's strict headers.
- New rule for `/games/(.*)` with a policy permissive enough to run canvas games, plus
  `X-Robots-Tag: noindex`. Candidate policy, to be confirmed by step 1:
  `default-src 'none'; script-src 'unsafe-inline' 'unsafe-eval' https://philaconvalley.com;
style-src 'unsafe-inline' fonts.googleapis.com; font-src fonts.gstatic.com;
img-src data: blob: https://philaconvalley.com; connect-src 'none';
frame-ancestors https://philaconvalley.com`. Explicit host rather than `'self'` for the
  opaque-origin reason below; `connect-src 'none'` because no launch game makes network
  calls and a game that starts to should be a visible review event.

Mutual exclusion is deliberate. `scripts/serve-with-headers.mjs` resolves overlapping rules
last-rule-wins, but Vercel's real precedence for overlapping rules is not something to bet
production security headers on. Non-overlapping sources cannot disagree.

### The sandbox / CSP collision — verify first

Games embed with `sandbox="allow-scripts"`, deliberately **without** `allow-same-origin`.
Combining the two is equivalent to no sandbox at all for same-origin content.

Consequence: the game document lands in an **opaque origin**, and in an opaque origin
**CSP `'self'` matches nothing.** A `/games/*` policy of `script-src 'self'` would block
Pigeon Post from loading its own vendored three.js. The carve-out must name an explicit
host or use `'strict-dynamic'`.

This interaction is the riskiest unknown in the feature and is proven in step 1 of the
build sequence, before anything is built on top of it.

Second consequence: Flappy's `localStorage` access throws in an opaque origin. Its high
score becomes session-only, guarded by `try`/`catch`. Persisting it would require
`postMessage` plumbing to the parent — out of scope.

### Fullscreen

The fullscreen button requires `allow="fullscreen"` plus `allowfullscreen` on the iframe.
It does not work by default on a sandboxed frame.

## 6. The repo auto-discovers built HTML — in two places

Both treat "an HTML file in `dist/`" as "a page of the website." Self-hosted games violate
that assumption, and **both fail the moment the game files land**, before any component
exists.

1. **`e2e/landmarks.spec.ts`** enumerates every `.html` in `dist/` by design ("so a page
   added later is covered without anyone remembering to add it here") and asserts exactly
   one `banner`, one `main`, one `contentinfo`. A bare canvas game has none.
2. **`scripts/check-csp-hashes.mjs`** walks all of `dist/` hashing inline scripts against
   the CSP allowlist, and runs as its own CI step.

Both need a `/games/` exclusion, each with a comment explaining that games are embedded
artifacts rather than pages. The exclusions ship in the same step as the game files.

## 7. Accessibility

Lighthouse runs as its own CI job and asserts `categories:accessibility` at **`error`,
≥0.9** — a real gate, not a warning.

- Add both `/arcade/` **and at least one `/arcade/<slug>/`** to `.lighthouserc.json`. The
  wall is static images; the iframe and all of its risk live on the cabinet pages.
- iframes carry a real `title`.
- The control legend is actual markup, not decoration.
- **Canvas games are not screen-reader accessible, and no page markup fixes that.** For an
  org centered on inclusion, the honest response is the required `longDescription` on every
  cabinet page — what the game is, how it plays — rather than a page that scores 0.9 while
  the game itself is unusable. State the limitation; do not engineer around the metric.
- **Keyboard escape.** The click-to-focus overlay hands keyboard control to a game that
  calls `preventDefault`. Without a documented way out, the cabinet is a keyboard trap — a
  WCAG failure. `Esc` returns focus to the page, with a visible instruction saying so.
- **Click-to-start is also the motion answer.** Nothing animates until the visitor opts in,
  which is the only honest option for motion-sensitive users on a page full of canvas
  animation the site cannot control from outside.

## 8. Known constraints in the launch games

- **Pong is 860×500 and never resizes** — its listeners are `click`, `keydown`, `keyup`
  only. Once cabinet chrome takes its share of a laptop viewport, the canvas may not fit.
  Needs a `transform: scale()` wrapper fitting the frame to available width.
- **Pong is unplayable on phones.** Its cabinet page detects this from `input` and says so
  outright, offering Flappy instead. No dead ends.
- **Pigeon Post is a demo, not a game.** Its own title calls it "a tiny-planet flight demo";
  there is no goal or score. `kind: demo` sets the expectation honestly.
- **three.js r128 is vendored** into `public/games/pigeon-post/vendor/`. Loading it from
  cdnjs would reintroduce exactly what commit `8b59b5e` removed. Upgrading off r128 is out
  of scope — it would require changing Diego's code.

## 9. Open item — licensing

**This blocks merge, not design.**

The repo is MIT. Committing the games licenses them to the world, permanently and
irrevocably. PhilaCon can only grant MIT if it owns the copyright. Diego is a contractor,
and unless his signed agreement contains an IP assignment or work-for-hire clause covering
this work, the copyright is his.

Resolve by confirming the clause, or by getting Diego's written sign-off on the PR that
adds the games.

## 10. Build sequence

0. **Confirm IP assignment with Diego.** Non-code. Blocks merge.
1. **Header carve-out plus its CSP test, first.** Proves a game can run in a frame at all —
   including the opaque-origin `'self'` interaction from §5 — against
   `scripts/serve-with-headers.mjs`, before anything depends on it.
2. **Vendor the games** into `public/games/`: three.js locally, `localStorage` guard in
   Flappy, Pong untouched. **Same step:** the `/games/` exclusions in `landmarks.spec.ts`
   and `check-csp-hashes.mjs` (§6), or CI breaks here.
3. `arcade` collection, schema, three markdown entries.
4. `scripts/capture-arcade-shots.mjs` — deterministic thumbnails and og:images. Games
   animate, so capture needs a scripted warm-up and fixed wait, not a random frame.
5. `ArcadeCabinet` + wall page + nav item.
6. `CabinetFrame` + cabinet page: click-to-focus overlay, `Esc` escape, fullscreen grants,
   scale wrapper for `fixedSize`, phone fallback.
7. Docs — `design-system.md` gets the cabinet; `adding-content.md` gets the submission bar
   (self-contained, no CDN dependencies, no network calls).
8. `.lighthouserc.json` — add `/arcade/` and one cabinet page.
9. e2e — extend `csp.spec.ts` (its `PAGES` list is hardcoded) for the carve-out and
   `noindex`; new `arcade.spec.ts` for cabinet count, sandbox attributes, keyboard escape,
   and the mobile Pong fallback.

Steps 1 and 4 carry the remaining risk. Everything from step 5 on is ordinary component work.

---

## 11. Explicitly out of scope

Accounts, leaderboards, play-count analytics, a submission form, external-origin hosting,
upgrading three.js, and any dark mode.
